# Working agreement

When the user supplies a failure screenshot or asks to solve a project problem,
treat it as an instruction to investigate and carry the authorized work through
implementation and verification. Do not ask whether to begin.

Read the relevant code, workflow runs, logs and recent changes. Use repository
records for continuity when earlier conversation context is unavailable. State
missing context honestly instead of claiming to remember it.

Make routine, reversible implementation choices autonomously. Prepare a concrete,
tested change and follow the repository's review and merge requirements. Ask only
when a missing decision, access, or required authorization actually blocks progress;
name the exact blocker and request the smallest necessary input.

Report outcomes with evidence: cause, changes, validation and remaining blockers.
Distinguish implemented, merged, configured and verified in a real run. Do not call
a scheduled integration complete while required configuration remains absent.

Preserve private evidence and reviewer independence. Never fabricate artifacts,
approvals or expiry renewals to make checks pass, suppress failures to imply
readiness, publish private account data, or expand trading execution permissions
as part of a maintenance fix.
